# Compx 8K 无线鼠标电量读取 — IOKit 方式可行性调查报告

> **调查日期**: 2026-08-17
> **设备**: Compx Wireless mouse 8k NANO dongle-L（VID `0x373B` / PID `0x11FE`，十进制 14139 / 4606）
> **连接方式**: 2.4G 无线（USB NANO 接收器直插 MacBook）
> **目的**: 确认是否可通过 **IOKit** 方式取得该鼠标的**电量**与**充电状态**
> **参考**: [技术文档.md](技术文档.md)、[Jingzao-JZM5-Battery/README.md](../../../ThirdPartySourceCode/macos-App/Jingzao-JZM5-Battery/README.md)

---

## 1. 结论（TL;DR）

**无法通过 IOKit 方式取得该鼠标的真实电量和充电状态。**

无论鼠标处于**休眠**还是**活跃**状态，IOKit 的 Input Report 回调都只能收到**接收器（dongle）本地的响应**，响应中不包含真实电量数据（`dataValidLen` 恒为 `0xFF` 或 `0`，`batteryLevel` / `batteryCharge` 字段无效）。

只有 **WebHID**（Chrome 直接读取 USB interrupt endpoint 原始数据）能收到鼠标通过私有 2.4G 无线链路转发的**真实电量**（`dataValidLen=2, batteryLevel=40`）。

## 2. 测试环境与方法

| 项目 | 值 |
| --- | --- |
| 操作系统 | macOS（Apple Silicon / arm64） |
| 工具 | Python + ctypes 调用 IOKit（`iokit_battery.py`，与 JZM5BatteryTray.swift 同思路） |
| 匹配条件 | `kIOHIDVendorIDKey=0x373B`, `kIOHIDProductIDKey=0x11FE` |
| 目标接口 | macOS 枚举出的厂商自定义接口 `UsagePage 0xFF05 / Usage 0x0000` |
| 查询命令 | Output Report `rid=0x08`，16 字节命令包，`commandId=0x04`（GetBatteryLevel），`checkSum=0x49` |
| 接收方式 | `IOHIDDeviceRegisterInputReportCallback` + RunLoop |

复刻网页驱动（hub.atk.pro）的初始化命令序列后再查询：`0x10 → 0x12 → 0x03 → 0x04 → 0x01 → 0x1D`。

## 3. 实测结果

### 3.1 设备枚举（hidutil / IOHIDManagerCopyDevices）

macOS 上该接收器枚举出 3 个 USB HID 接口：

| UsagePage | Usage | 说明 |
| --- | --- | --- |
| `0x0001` | `0x0002` | 标准鼠标（Generic Mouse） |
| `0x0001` | `0x0006` | 标准键盘（Generic Desktop / Keyboard） |
| `0xFF05` | `0x0000` | **厂商自定义接口**（承载私有协议，本次测试目标） |

### 3.2 Report Descriptor 检查（是否暴露标准 HID Battery 接口）

读取 3 个接口的 HID Report Descriptor：

| UsagePage | Descriptor 长度 | 含标准 Battery Page(0x84/0x85) |
| --- | --- | --- |
| `0x0001/0x0002` | 87 B | ❌ 无 |
| `0x0001/0x0006` | 57 B | ❌ 无 |
| `0xFF05/0x0000` | 266 B | ❌ 无（含 vendor page 0xFF05） |

> **结论**：接收器**没有暴露标准 HID 电池接口**，无法通过 macOS 标准电池 usage 途径读取，只能走私有协议。

### 3.3 私有协议 — IOKit 查询实测

发送 `rid=0x08` + `[04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 49]` 后，IOKit 回调收到的响应如下。

#### (a) 鼠标休眠时

```
08 04 00 FF FF FF FF FF <ASCII递增序号> 00 00 00 00 00 00 00 00
```

实测多轮（序号递增，十进制 ASCII 计数）：

```
第 1 次: 08 04 00 ff ff ff ff ff 31 00 00 00 00 00 00 00 00
第 2 次: 08 04 00 ff ff ff ff ff 32 00 00 00 00 00 00 00 00
...
第 9 次: 08 04 00 ff ff ff ff ff 39 00 00 00 00 00 00 00 00
第10 次: 08 04 00 ff ff ff ff ff 31 30 00 00 00 00 00 00 00
```

| 偏移 | 值 | 含义 |
| --- | --- | --- |
| `[0]` | `0x08` | Report ID |
| `[1]` | `0x04` | commandId 回显 |
| `[2]` | `0x00` | commandStatus（成功） |
| `[3..7]` | `FF FF FF FF FF` | **休眠标志 / dataValidLen 区域 = 0xFF** |
| `[8..9]` | ASCII 递增数字 | 查询序号（"1"→"10"→"11"…） |

> `dataValidLen = 0xFF` → **无效数据**，无真实电量。

#### (b) 鼠标活跃时（移动/点击鼠标唤醒后）

```
08 04 00 00 00 00 00 00 30 34 00 00 00 00 00 00 A0
```

| 偏移 | 值 | 含义 |
| --- | --- | --- |
| `[0]` | `0x08` | Report ID |
| `[1]` | `0x04` | commandId 回显 |
| `[2]` | `0x00` | commandStatus（成功） |
| `[3..7]` | `00 00 00 00 00` | 活跃标志 |
| `[5]` | `0x00` | **dataValidLen = 0** |
| `[6]` | `0x00` | batteryLevel = 0（无效） |
| `[7]` | `0x00` | batteryCharge = 0（无效） |
| `[8..9]` | `0x30 0x34` = ASCII `"04"` | **dongle 本地回显命令号** |
| `[15]` | `0xA0` | 状态/校验 |

> **关键点**：`[8..9]` 的 `0x30 0x34` 是 ASCII 字符 `"04"`（即命令号），不是电压或电量。`dataValidLen=0` → **仍无有效电量**。
>
> ⚠️ 若按 WebHID 的偏移 +1 误解析，会把 `0x34 0x30` 当成电压 `0x3430 = 13360 mV`，这是**假数据**，必须通过 `dataValidLen >= 1` 校验排除。

### 3.4 WebHID 对照（真实电量，技术文档已验证）

通过 Chrome WebHID（hub.atk.pro 网页驱动）发送相同命令，能收到鼠标转发的真实电量：

```
04 00 00 00 02 28 00 0f 4e 00 00 00 00 00 00 c2
```

| 偏移 | 值 | 含义 |
| --- | --- | --- |
| `[0]` | `0x04` | commandId |
| `[1]` | `0x00` | commandStatus（成功） |
| `[4]` | `0x02` | **dataValidLen = 2（有效）** |
| `[5]` | `0x28` = **40** | **batteryLevel（电量 40%）** |
| `[6]` | `0x00` | **batteryCharge（0 = 未充电）** |
| `[7..8]` | `0x0F4E` = 3918 | batteryVoltage（mV） |
| `[15]` | `0xC2` | checkSum |

> 同一物理接收器、同一命令，**IOKit 与 WebHID 收到的响应完全不同**。

## 4. 结论与原因分析

### 4.1 结论

| 读取方式 | 能否取得真实电量/充电状态 |
| --- | --- |
| IOKit（IOHIDManager / IOHIDDevice 私有协议） | ❌ **不能** |
| 标准 HID Battery usage（0x84/0x85） | ❌ 无此接口 |
| WebHID（Chrome CDP / hub.atk.pro） | ✅ **能**（已验证 40%） |

### 4.2 根因分析

1. **macOS 的 HID Event System** 对厂商自定义 Usage Page 的 Input Report 路由方式与 Chrome 的 WebHID 实现不同：
   - **WebHID** 直接读取 USB interrupt endpoint 的原始数据，能收到**接收器转发的鼠标真实数据**；
   - **IOKit** 回调收到的是**接收器（dongle）固件本地生成的响应**（含 `"open"` 字样、ASCII 命令号回显、`0xFF`/`0x00` 无效数据），并不转发鼠标无线链路的真实电量。
2. 该接收器固件**只在收到 WebHID 风格的原始读取时**才会把 2.4G 无线链路上鼠标返回的电量数据回传给主机；IOKit 抽象层拿不到这份数据。
3. 与 **JZM5（京东京造）** 对比：JZM5 接收器（VID `0x362D` / PID `0xD107`）在 IOKit 下能直接收到真实电量（`payload[19] & 0x7F`），因此 JZM5 项目的 IOKit 方案可行；但 **Compx 8K 接收器固件行为不同，IOKit 方案不适用**。这也与 README 中"仅适配京东京造 JZM5，不适用于其他型号"的限定一致。

## 5. 后续方案建议

若要为 Compx 8K 开发独立的 macOS 菜单栏/托盘电量程序，可选：

| 方案 | 可行性 | 说明 |
| --- | --- | --- |
| **A. Chrome CDP + WebHID**（推荐） | ✅ 已验证 | 以远程调试模式启动 Chrome，在 hub.atk.pro（或内嵌 WebHID 页面）中执行 JS 读取电量。缺点：依赖 Chrome 常驻、首次需授权设备。 |
| B. IOKit / USB 底层绕过 | ⚠️ 未验证 | `IOUSBHostInterface` 直接访问 USB endpoint 绕过 HID Event System。复杂度高，可能需要特殊权限，不保证成功。 |
| C. 仅适配 JZM5 的现成方案 | ✅ 但型号不符 | 保留原 JZM5BatteryTray.swift 不变（它只适用于 JZM5 接收器）。 |
